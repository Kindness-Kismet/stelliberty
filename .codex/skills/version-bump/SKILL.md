# 更新版本

先阅读根目录 `AGENTS.md` 和同级 `../commit/SKILL.md`，使用项目实际架构与配置来源；需要推送时阅读同级 `../git-push/SKILL.md`，按实际授权次数执行。

验证按 AGENTS 的工程入口与实际影响选择。版本目标、依赖策略和日志覆盖等准备操作沿用已确认的范围与内容，发生实质变化时补充确认；推送许可由 git-push skill 单独核对。

## 发布准备约定

版本来源、派生消费者、更新日志位置、发布渠道与验证入口从 AGENTS 的配置来源和工程入口确认；当前仓库版本从 HEAD 读取。

- 版本格式与提升规则：三段数字版本；默认补丁号加一，指定版本必须高于当前版本
- 更新日志语言与维护模式：全量重写当前发布摘要，英文在上、单行 `---` 分隔、简体中文在下；数量、顺序与含义对应
- 依赖更新策略：版本提升不自动升级依赖；NuGet、Cargo 与锁文件变化采用另行明确的依赖任务范围
- 发布基线判定：用 `git log --follow -S` 核对将上一版本改为 HEAD 当前版本的唯一版本提交，确认其位于当前历史；标签只辅助核验

## 执行流程

1. 检查当前分支、HEAD、工作区和暂存区；确认用户请求对应的发布范围。
2. 确认每项改动的归属，将属于本次范围的业务改动按通用提交规则分别处理，版本元数据和日志保留到版本提交。
3. 从 HEAD 中的唯一版本源读取当前仓库版本，工作区目标版本单独读取并核对提升规则。
4. 根据已确认的发布标识与实际版本历史确定唯一发布基线，核对它位于当前历史中，并从该基线读取已发布版本；第1次发布或基线待明确时先确认范围，再确定本次目标。
5. 对比发布基线到当前最终代码，归纳仍然生效的用户变化，同一功能反复修正合并为1条。
6. 按已确认的依赖更新策略选择需要更新的包，在相应授权范围内获取依赖。
7. 修改唯一版本源，通过实际生成或配置入口更新生成头、平台资源、包清单等派生字段；独立组件版本按自身发布策略维护。
8. 按项目确认的重写或追加规则更新日志；涉及覆盖用户已有内容时，先确认覆盖目标与内容，沿用已覆盖本次操作的明确确认。
9. 按变更范围核对 AGENTS 的实际架构与桥接，代码约束和文件上限按同级 `../code-style/SKILL.md` 检查，并执行必要格式化、实际验证与技能同步；超限先拆分，失败保留证据，验证通过后进入暂存与提交。
10. 本次版本提交纳入版本源、必要派生元数据与本次日志；业务、依赖升级和独立的格式化调整使用各自逻辑提交。
11. 完成暂存白名单、隐私与版本一致性核对，创建本地版本提交并核对实际内容。

版本提交标题统一为 `chore: bump version to <新版本> and update changelog`；需要正文时准确描述最终结果。

## 日志与 issue

- 发布日志围绕普通用户能感知的功能、行为、界面、修复和性能变化组织。
- 双语发布日志采用项目已确认格式，保持数量、顺序和语义一一对应，内容以最终生效的变化为准。
- 同一变化集中描述最终效果；本次用户可见变化为空时如实说明。
- 关联 issue 前阅读原文并核对实际交付，按实际完成查询的范围报告检查结果。
- 完整满足 issue 要求且证据充分时使用关闭关键词；其余情况采用引用或省略关联。

## 项目日志格式

- 当前日志全量重写，不追加历史版本、日期或分类标题；每条以 `- ` 开头，末尾不加标点。
- 中英文条目按修复、改善、新增、移除或调整的真实最终结果描述。
- 独立格式化变化与版本元数据分别提交；版本提交只纳入唯一版本源和当前日志，确有生成输入变化时纳入其必要派生文件。

## 完成与维护

暂存与提交前确认版本源唯一、格式与目标明确、发布基线已核对、HEAD 位于目标分支、改动归属清楚、必要验证通过；涉及覆盖已有内容时，确认授权覆盖本次目标与内容。前提待补齐时，暂停依赖该前提的操作，报告实际状态与下一步。

完成后检查 `git status --short` 和最新提交，确认应用版本、文件名、日志和提交范围一致，并报告实际执行的验证。
